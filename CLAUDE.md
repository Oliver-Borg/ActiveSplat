# ActiveSplat – notes for Claude

## GPU etiquette (shared machine: 4× L40S, other users)

- **Always check `nvidia-smi` right before launching any GPU job.** Never start a job on a GPU that has another user's process on it or non-trivial memory/utilisation in use. See who owns each GPU process:
  ```bash
  nvidia-smi --query-gpu=index,uuid,memory.used,utilization.gpu --format=csv,noheader
  nvidia-smi --query-compute-apps=gpu_uuid,pid,used_memory --format=csv,noheader \
    | while IFS=', ' read -r uuid pid mem _; do echo "$uuid $mem MiB $(ps -o user=,cmd= -p $pid 2>/dev/null | cut -c1-80)"; done
  ```
  If the GPUs are busy, wait or ask the user. Don't squeeze in alongside someone else.
- **Long-running jobs (anything over ~15 min, e.g. full 1000+ step runs) may use at most 2 GPUs at once**, even when all 4 look free. Queue the rest instead of spreading across all 4. Short smoke tests may use a free GPU beyond that, but check first all the same.
- Pin a job to a GPU with `CUDA_VISIBLE_DEVICES=N` **and** `gpu_id:=0` / `--gpu_id 0`. Open3D in this env sees only one device, so `gpu_id:=1..3` crashes the mapper ("Invalid CUDA Device").

## Running scenes

- Machine is headless: always pass `hide_mapper_windows:=1 hide_planner_windows:=1`; use `save_runtime_data:=1` to get images to look at.
- Give each concurrent run its own ROS master: `export ROS_MASTER_URI=http://localhost:<port>` and `roslaunch -p <port> ...`.
- `roslaunch` does not exit after the nodes finish. Wait for `mapper node finished`, then send SIGINT. The mapper always ends with an Open3D "leaking memory blocks on CUDA:0" abort (exit -6) *after* saving; that is harmless.
- Configs: `config/datasets/gibson*.json`; `*_high_resolution.json` = 512² sensor + 10 mapping iters. Dataset roots live in `config/user_config.json` (gitignored; currently points `gibson` at the Habitat test scenes).
- Dataset configs must live in `config/datasets/`: paths inside them (e.g. `env.config`) resolve relative to the repo, via the config file's location.
- `mapper.gaussian_seeding.method`: `depth` (default when the block is absent) or `vggt_omega`, which seeds new Gaussians from VGGT-Ω depth (scaled to the sensor depth's median) with kNN scales; SplaTAM still optimises them. VGGT-Ω runs in its own env (`vggt-omega`, py3.11, torch 2.6, `pip install -e ~/work/git/vggt-omega`) as a worker process (`src/mapper/vggt_omega/worker.py`) on the same GPU. Example: `config/datasets/gibson_high_resolution_vggt_omega.json`. Checkpoint is gated on Hugging Face (facebook/VGGT-Omega); an empty `checkpoint` uses random weights (plumbing tests only). VGGT-Ω runs also write `pose_errors.csv`: VGGT-Ω's predicted pose of each window frame relative to the current frame vs. the true pose (translations scaled by the depth-alignment factor). Mapper poses themselves are the simulator's and never optimised, so sensor-depth runs have no pose error.
- Image quality is evaluated at the end of every run, in the visualizer (`src/evaluation/image_eval.py`): the final map is rendered at the captured poses (the sensor frames are kept in memory every `trajectory_stride`-th step) and at novel poses near the trajectory (simulator teleports), and compared with the simulator's view there. Nothing but `image_metrics.{csv,json}` and a few JPEG panels in `image_eval/` is written. Tune or disable with an optional `image_eval` block in the dataset config (`enabled`, `trajectory_stride`, `novel_views`, `novel_radius`, `examples`, `seed`). `scripts/judges/eval_images.py` does the same offline for finished runs (replays `actions.txt`); it skips runs that already have `image_metrics.json` unless `--force`.
- Images saved for looking at (top-down maps, `render_rgbd`, opacity images, `gaussians_data/rgb`, keyframes, eval panels) are JPEGs (`utils.imwrite_jpeg`, quality 90); depth stays 16-bit PNG. Older runs have PNGs; the dashboard reads both.
- Evaluate a run: `python scripts/judges/eval_actions.py --save_path $r/actions_error.txt --config $r/config.json --user_config config/user_config.json --actions $r/actions.txt --gpu_id 0`.
- `gaussians_data/transforms.json` has zero translation for every frame. Use the poses in `gaussians_data/params.npz` (`cam_unnorm_rots`, `cam_trans`, w2c) instead.

## Python environments

- The shell's `PYTHONPATH` points at the `ActiveSplat` env's site-packages (catkin workspace is sourced). Run any **other** env's `pip`/`python` with `env -u PYTHONPATH`, or pip will uninstall packages from the ActiveSplat env. Run `pip check` there after any install.
- Results dashboard: separate env `activesplat-dash` (py3.11, gradio 5), launched with `scripts/tools/dashboard.sh` (port 7860). The Videos tab encodes `<run>/videos/*.mp4` from the runtime frames with `imageio-ffmpeg` (bundled ffmpeg, installed in that env); `render_rgbd` is the Gaussian map rendered at the drone's pose, the sensor view is `gaussians_data/{rgb,depth}`. The "Real-time video" section of that tab builds `<run>/videos/realtime_<N>x.mp4`: sensor view plus top-down maps, timed with user-set forward/turn speeds and per-step stop-and-capture time (step size and turn angle read from the run's habitat env yaml).
- Tracing: each node writes real spans (pid, tid, nesting by time containment) with `utils.tracer` (`tracer.span(...)`, `begin()`/`finish()`, `@tracer.traced(...)`; no-op until `tracer.open(results_dir, process_name)`) to `<run>/trace_<process>.jsonl`; `TimingRecorder.record` also emits a span unless `trace=False` (use that when you write the span yourself or the time is derived). `python scripts/tools/timeline.py <run> [--perfetto]` draws it (PNG, and `trace.json` for https://ui.perfetto.dev); the dashboard Timeline tab shows it interactively. Spans in `DEBUG_SPANS` / `WAITING_SPANS` (timeline.py) are drawn as visualisation-only / waiting.
- Top-down map renders are cached in the visualizer (free map keyed by mapper steps + height cut, visible map by its snapshot) and skip the rasterizer's unused second pass. `ACTIVESPLAT_VERIFY_TOPDOWN=1` re-renders every map the original way and compares bitwise (the stats are logged at the end of the run); use it after touching the render path. Native-planner runs are not bit-reproducible: with the same seed two runs agree for ~250 steps and then diverge, so compare actions/coverage statistically, not exactly.
- Performance optimisations are individually switchable (`src/utils/optimisations.py`) with the environment variable `ACTIVESPLAT_OPTIMISATIONS` (inherited by every node): unset/`all`, `baseline` (none), `-render_cache,-snapshot_cache` (all except), or `render_cache,single_pass_render` (only these). Names: `single_pass_render`, `prepared_params` (needs the former), `render_cache`, `snapshot_cache`, `no_clone_cut`. The mapper writes the resolved set and a label to `<run>/optimisations.json`, shown in the dashboard run list/summary and the timeline titles; runs without the file predate the switches (`baseline` = code before ac46440). Add a new optimisation by registering it in `OPTIMISATIONS` and guarding the code with `optimisations.enabled(name)`, keeping the old path as the baseline.
- JPEG output of visualisation images is not switchable: it is always on, to save disk space on the cluster.
- Simulated odometry error (`src/utils/pose_noise.py`): an optional `pose_noise` block in the dataset config (`enabled`, `translation_drift`, `rotation_drift` as fractions of distance / angle moved, `jitter_m`, `jitter_deg`, `seed`), or `ACTIVESPLAT_POSE_NOISE='{"translation_drift":0.01,"rotation_drift":0.01}'` (also enables it), gives the mapper and planner drifting poses built from the true relative motion; the dataset thread applies it once per accepted frame. Evaluation stays true: the in-run image eval renders the map at the views' true poses mapped through the rigid ATE alignment of the trajectory, the oracle and the saved `eval_actions` point clouds (rebuilt from simulator frames) use true poses. `pose_noise.json` in the run holds the settings and ATE / rotation errors. Don't combine it with the oracle look-around (it renders at the drifted pose). `transforms.json` / `params.npz` poses are the estimated ones. Example (150 steps, 2 % drift + 5 mm / 0.3° jitter, gZ6f7yhEvPG): trajectory PSNR 25.0 -> 16.3.
